# Phase 22: Infrastructure Foundation - Research

**Researched:** 2026-03-05
**Domain:** AWS CDK v2 TypeScript -- VPC, RDS PostgreSQL, S3, ECR, ALB, Secrets Manager, SSM, VPC Endpoints
**Confidence:** HIGH

## Summary

This phase provisions all AWS infrastructure via a single CDK TypeScript stack. The CDK v2 library (`aws-cdk-lib`) provides L2 constructs for every resource needed: `Vpc`, `DatabaseInstance`, `Bucket`, `Repository`, `ApplicationLoadBalancer`, `SecurityGroup`, `InterfaceVpcEndpoint`, `GatewayVpcEndpoint`, `StringParameter`, and `Secret`. The project already has detailed architecture decisions in CONTEXT.md and ARCHITECTURE.md -- this research focuses on CDK-specific implementation patterns, construct APIs, and pitfalls.

The single hardest part of this phase is the DATABASE_URL secret composition. CDK's `rds.Credentials.fromGeneratedSecret()` stores credentials as a JSON object (`{username, password, host, port, dbname, engine}`), not a composed connection string. ECS can inject individual secret fields, but the app expects a single `DATABASE_URL` string. The recommended approach is to create a second Secrets Manager secret that constructs the URL from the RDS instance's endpoint properties and the generated password.

**Primary recommendation:** Use CDK L2 constructs exclusively (no L1/CloudFormation resources). Initialize with `cdk init app --language typescript` in the `infra/` subdirectory. Single stack, single `cdk deploy` command.

### Pattern 1: VPC with Three Subnet Tiers
**What:** Three subnet types -- PUBLIC (for NAT/ALB), PRIVATE_WITH_EGRESS (for ECS/ALB), and PRIVATE_ISOLATED (for RDS).
**When to use:** Internal applications needing outbound internet and database isolation.
**Example:**
```typescript
// Source: AWS CDK Vpc construct docs
import * as ec2 from 'aws-cdk-lib/aws-ec2';

const vpc = new ec2.Vpc(this, 'Vpc', {
  vpcName: 'requirements-foundry-prod-vpc',
  ipAddresses: ec2.IpAddresses.cidr('10.0.0.0/16'),
  maxAzs: 2,
  natGateways: 1, // Single NAT for POC cost savings
  subnetConfiguration: [
    {
      cidrMask: 24,
      name: 'public',
      subnetType: ec2.SubnetType.PUBLIC,
      // NAT Gateway lives here. ALB can also go here for internal ALBs.
    },
    {
      cidrMask: 24,
      name: 'application',
      subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS,
      // ECS tasks, ALB (internal) go here
    },
    {
      cidrMask: 24,
      name: 'database',
      subnetType: ec2.SubnetType.PRIVATE_ISOLATED,
      // RDS instance goes here -- no internet access at all
    },
  ],
});
```

**Key detail:** `natGateways: 1` places a single NAT in one AZ. Cross-AZ traffic incurs small charges but acceptable for POC. The PUBLIC subnet is required for the NAT Gateway's internet gateway route, even though no resources are directly internet-facing.

### Pattern 2: Security Group Chain (ALB -> ECS -> RDS)
**What:** Three security groups that reference each other, creating a strict network boundary chain.
**When to use:** Any tiered architecture where components should only accept traffic from the tier above.
**Example:**
```typescript
import * as ec2 from 'aws-cdk-lib/aws-ec2';

const albSg = new ec2.SecurityGroup(this, 'AlbSg', {
  vpc,
  securityGroupName: 'requirements-foundry-prod-alb-sg',
  description: 'ALB accepts corporate network traffic',
  allowAllOutbound: true,
});
// RFC1918 ranges for corporate network
albSg.addIngressRule(ec2.Peer.ipv4('10.0.0.0/8'), ec2.Port.tcp(80), 'Corporate 10.x');
albSg.addIngressRule(ec2.Peer.ipv4('172.16.0.0/12'), ec2.Port.tcp(80), 'Corporate 172.x');
albSg.addIngressRule(ec2.Peer.ipv4('192.168.0.0/16'), ec2.Port.tcp(80), 'Corporate 192.x');

const ecsSg = new ec2.SecurityGroup(this, 'EcsSg', {
  vpc,
  securityGroupName: 'requirements-foundry-prod-ecs-sg',
  description: 'ECS accepts ALB traffic only',
  allowAllOutbound: true,
});
ecsSg.addIngressRule(albSg, ec2.Port.tcp(3000), 'From ALB on port 3000');

const rdsSg = new ec2.SecurityGroup(this, 'RdsSg', {
  vpc,
  securityGroupName: 'requirements-foundry-prod-rds-sg',
  description: 'RDS accepts ECS traffic only',
  allowAllOutbound: false, // RDS doesn't need outbound
});
rdsSg.addIngressRule(ecsSg, ec2.Port.tcp(5432), 'From ECS on port 5432');

const endpointSg = new ec2.SecurityGroup(this, 'EndpointSg', {
  vpc,
  securityGroupName: 'requirements-foundry-prod-endpoint-sg',
  description: 'VPC endpoints accept ECS traffic',
  allowAllOutbound: false,
});
endpointSg.addIngressRule(ecsSg, ec2.Port.tcp(443), 'From ECS on HTTPS');
```

### Pattern 3: RDS with Auto-Generated Credentials
**What:** Let CDK generate the RDS master password and store it in Secrets Manager automatically.
**When to use:** Always -- never hardcode database passwords.
**Example:**
```typescript
import * as rds from 'aws-cdk-lib/aws-rds';
import * as ec2 from 'aws-cdk-lib/aws-ec2';

const dbInstance = new rds.DatabaseInstance(this, 'Database', {
  instanceIdentifier: 'requirements-foundry-prod-rds',
  engine: rds.DatabaseInstanceEngine.postgres({
    version: rds.PostgresEngineVersion.VER_16_3,
  }),
  instanceType: ec2.InstanceType.of(
    ec2.InstanceClass.BURSTABLE4_GRAVITON,
    ec2.InstanceSize.MICRO,
  ),
  vpc,
  vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_ISOLATED },
  securityGroups: [rdsSg],
  databaseName: 'requirements_foundry',
  credentials: rds.Credentials.fromGeneratedSecret('postgres', {
    secretName: 'requirements-foundry-prod/rds-credentials',
  }),
  allocatedStorage: 20,
  maxAllocatedStorage: 50,
  multiAz: false,
  deletionProtection: false, // POC -- allow teardown
  removalPolicy: cdk.RemovalPolicy.DESTROY, // POC -- delete on stack destroy
});
```

### Pattern 4: DATABASE_URL Secret Composition
**What:** The RDS-generated secret stores JSON fields (`{username, password, host, port, dbname}`), not a composed URL. Create a separate secret that constructs the `DATABASE_URL` for ECS injection.
**When to use:** When app expects a single connection string (like Prisma's `DATABASE_URL`).
**Example:**
```typescript
import * as secretsmanager from 'aws-cdk-lib/aws-secretsmanager';

// The RDS instance creates dbInstance.secret automatically
// But it stores { username, password, host, port, dbname, engine }
// ECS needs a single DATABASE_URL string

// Approach: Create a second secret with the composed URL
// The actual URL value must be set post-deploy (or via a Custom Resource)
// because the password is only known at deploy time

// Option A: Use CDK's secret field references in ECS task definition (Phase 23)
// ECS can inject individual fields: ecs.Secret.fromSecretsManagerVersion(secret, { field: 'password' })
// Then compose in the Docker entrypoint

// Option B: Store a template and resolve at container startup
const databaseUrlSecret = new secretsmanager.Secret(this, 'DatabaseUrlSecret', {
  secretName: 'requirements-foundry-prod/database-url',
  description: 'DATABASE_URL for the application',
  // Value will be set by a post-deploy script or Custom Resource
});

// Grant the ECS task execution role read access (Phase 23 wires this)
```

**Recommended approach for this POC:** Use a Docker entrypoint wrapper script that reads the RDS secret JSON fields (injected by ECS as individual env vars via `ecs.Secret.fromSecretsManager(secret, 'field')`) and composes the DATABASE_URL at container startup. This avoids Custom Resources and keeps the CDK stack simple.

### Pattern 5: Internal ALB with Default Action
**What:** Deploy an internal ALB that returns 503 (no targets) until Phase 23 wires ECS. This validates network connectivity.
**Example:**
```typescript
import * as elbv2 from 'aws-cdk-lib/aws-elasticloadbalancingv2';

const alb = new elbv2.ApplicationLoadBalancer(this, 'Alb', {
  loadBalancerName: 'requirements-foundry-prod-alb',
  vpc,
  internetFacing: false, // Internal only
  securityGroup: albSg,
  vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
});

// Add HTTP listener with fixed 503 response (no targets yet)
const listener = alb.addListener('HttpListener', {
  port: 80,
  defaultAction: elbv2.ListenerAction.fixedResponse(503, {
    contentType: 'text/plain',
    messageBody: 'Service not yet deployed',
  }),
});

// Create a target group that Phase 23 will attach ECS service to
const targetGroup = new elbv2.ApplicationTargetGroup(this, 'TargetGroup', {
  targetGroupName: 'requirements-foundry-prod-tg',
  vpc,
  port: 3000,
  protocol: elbv2.ApplicationProtocol.HTTP,
  targetType: elbv2.TargetType.IP, // Fargate uses IP targets
  healthCheck: {
    path: '/api/health',
    interval: cdk.Duration.seconds(30),
    healthyThresholdCount: 2,
    unhealthyThresholdCount: 3,
  },
});

// Add target group to listener as a rule or swap the default action later
```

### Anti-Patterns to Avoid
- **Using `ApplicationLoadBalancedFargateService` in Phase 22:** This L3 construct creates ECS service + ALB together. Phase 22 only creates the ALB; ECS is Phase 23 scope. Use separate L2 constructs.
- **Forgetting `removalPolicy: DESTROY` on stateful resources:** Default is RETAIN, which means `cdk destroy` leaves orphaned resources that block re-deploy (name conflicts).
- **Hardcoding account/region in the stack:** Use `env: { account: process.env.CDK_DEFAULT_ACCOUNT, region: process.env.CDK_DEFAULT_REGION }` or `env: { region: 'us-east-1' }`.
- **Creating public subnets without NAT Gateway:** CDK creates a NAT per AZ by default. Set `natGateways: 1` explicitly to avoid surprise costs ($32/month per NAT).
- **Using `PRIVATE_ISOLATED` for ECS subnets:** Isolated subnets have zero outbound internet. ECS needs `PRIVATE_WITH_EGRESS` for ECR pulls, npm packages, etc.
- **Forgetting S3 bucket removal policy:** Default RETAIN means `cdk destroy` fails if bucket has objects. For POC, use `removalPolicy: DESTROY` + `autoDeleteObjects: true`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| VPC with subnets, route tables, NAT | Manual route table associations | `ec2.Vpc` construct | Auto-creates subnets, route tables, NAT, IGW, all wiring |
| RDS credential management | Manual password in SSM/env | `rds.Credentials.fromGeneratedSecret()` | Auto-generates, stores in Secrets Manager, handles rotation |
| Security group rules | Manual IP-based rules | SG cross-references (`albSg` as peer) | CDK resolves SG IDs, handles circular refs |
| VPC endpoint routing | Manual route table entries | `GatewayVpcEndpoint` / `InterfaceVpcEndpoint` | CDK adds routes to correct route tables automatically |
| Subnet group for RDS | Manual `SubnetGroup` construct | `vpcSubnets` property on `DatabaseInstance` | CDK auto-creates the subnet group from subnet selection |
| ECR lifecycle policy JSON | Raw JSON policy document | `repository.addLifecycleRule()` | Type-safe, validates at synth time |

**Key insight:** CDK's L2 constructs handle 90% of the wiring automatically. The VPC construct alone creates 15+ CloudFormation resources (VPC, subnets, route tables, NAT, IGW, routes, EIPs). Don't try to recreate this with L1 constructs.

## Common Pitfalls

### Pitfall 1: Orphaned Resources on Re-Deploy
**What goes wrong:** `cdk destroy` followed by `cdk deploy` fails because resources with fixed names (S3 bucket, RDS instance) were retained and the new stack tries to create resources with the same names.
**Why it happens:** CDK defaults to `RemovalPolicy.RETAIN` for stateful resources (S3, RDS, Secrets Manager).
**How to avoid:** For POC, set `removalPolicy: cdk.RemovalPolicy.DESTROY` on S3 bucket, RDS instance, ECR repository, and secrets. Add `autoDeleteObjects: true` on S3 bucket.
**Warning signs:** CloudFormation rollback error mentioning "already exists".

### Pitfall 2: NAT Gateway Cost Surprise
**What goes wrong:** CDK creates one NAT Gateway per AZ by default. With 2 AZs that's $64/month just for NAT.
**Why it happens:** `natGateways` defaults to the number of AZs if not specified.
**How to avoid:** Explicitly set `natGateways: 1` in the VPC construct.
**Warning signs:** AWS bill shows multiple NAT Gateway charges.

### Pitfall 3: CDK Bootstrap Not Run
**What goes wrong:** `cdk deploy` fails with "This stack uses assets, so the toolkit stack must be deployed".
**Why it happens:** CDK needs a bootstrap stack (S3 bucket + ECR repo for assets) in the target account/region.
**How to avoid:** Run `cdk bootstrap aws://ACCOUNT_ID/us-east-1` once before first deploy.
**Warning signs:** Error message about "CDKToolkit" stack.

### Pitfall 4: RDS Secret vs DATABASE_URL Mismatch
**What goes wrong:** App gets `{username, password, host, port, dbname}` JSON but expects `postgresql://user:pass@host:5432/db`.
**Why it happens:** `Credentials.fromGeneratedSecret()` stores a JSON object, not a connection string.
**How to avoid:** Either (a) create a separate secret with composed URL via Custom Resource, or (b) inject individual fields into ECS and compose at container startup via entrypoint script.
**Warning signs:** App fails to connect to database despite secret existing.

### Pitfall 5: Security Group Circular Dependencies
**What goes wrong:** CDK synth fails with circular dependency error when two security groups reference each other.
**Why it happens:** SG-A allows ingress from SG-B, and SG-B allows ingress from SG-A.
**How to avoid:** Use `addIngressRule()` after both SGs are created (CDK resolves this correctly for the ALB->ECS->RDS chain since it's one-directional).
**Warning signs:** CDK synth error mentioning "dependency cycle".

### Pitfall 6: Internal ALB Not Reachable
**What goes wrong:** ALB deployed but returns "connection refused" from corporate network.
**Why it happens:** ALB is in private subnets with no route from corporate network (VPN/Direct Connect not configured).
**How to avoid:** Verify corporate VPN/Direct Connect routing reaches the VPC CIDR (10.0.0.0/16). This is an infra-team dependency, not a CDK issue.
**Warning signs:** `curl` to ALB DNS name times out.

### Pitfall 7: VPC Endpoint Security Group Missing
**What goes wrong:** Bedrock calls from ECS fail despite VPC endpoint existing.
**Why it happens:** Interface VPC endpoints need a security group allowing inbound HTTPS (443) from the ECS security group.
**How to avoid:** Create a dedicated `endpointSg` that allows TCP/443 from `ecsSg`.
**Warning signs:** Bedrock SDK timeout errors from ECS tasks.

## Open Questions

   - What we know: ALB will be internal, security group allows RFC1918 ranges
   - What's unclear: VPN/Direct Connect/Transit Gateway routing from corporate network to VPC not confirmed
   - Recommendation: Deploy the stack, output the ALB DNS name, and coordinate with infra team to verify routing. This is a dependency external to CDK.

2. **DATABASE_URL composition strategy**
   - What we know: RDS secret stores JSON fields, app expects a composed URL
   - What's unclear: Whether to use Custom Resource, entrypoint script, or Phase 23 ECS task definition approach
   - Recommendation: For Phase 22, create the RDS instance and let CDK auto-generate the secret. Phase 23 will handle injecting the composed URL into the ECS container (most likely via entrypoint script that reads individual fields). Phase 22 should export the RDS secret ARN for Phase 23 to consume.

3. **PostgreSQL version selection**
   - What we know: CDK supports VER_16_3 and VER_17_7; project uses Prisma 7.2.0
   - What's unclear: Whether Prisma 7.2.0 fully supports PostgreSQL 17
   - Recommendation: Use `VER_16_3` (PostgreSQL 16) as the safe, well-tested choice. PostgreSQL 16 is current LTS and has full Prisma compatibility.

4. **ALB listener protocol (HTTP vs HTTPS)**
   - What we know: Architecture doc mentions HTTPS/443 on ALB with ACM cert
   - What's unclear: Whether ACM certificate exists or needs creation; internal apps sometimes skip HTTPS
   - Recommendation: Start with HTTP/80 for Phase 22 to validate connectivity. HTTPS can be added later with ACM cert (or in Phase 23 when the full service is wired up).
